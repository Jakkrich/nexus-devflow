# บทที่ 6: พิสูจน์ผลลัพธ์และเปิด PR

คำว่า "It compiles" (คอมไพล์ผ่านแล้ว) ไม่ใช่หลักฐาน หลักการ [Prove It Works](../../../skills/principle-prove-it-works/SKILL.md) บังคับให้ agent ตรวจสอบของจริงก่อนรายงานความสำเร็จ และหน้าที่ของคุณคือทำให้ "ของจริง" นั้นตรวจสอบได้ บทนี้ครอบคลุมตั้งแต่การตั้งเงื่อนไขจบงาน การเช็กความน่าเชื่อถือของตัวเลขวัดผล การสร้าง verification skill ประจำแอปของคุณ การทำ formal verification สำหรับคุณสมบัติที่ test เข้าไม่ถึง ไปจนถึงการเปิด PR และพาไปจน merge สำเร็จ

การตรวจสอบผลลัพธ์คือขั้นตอนที่ช้าที่สุดในการทำงานกับ agent ส่วนใหญ่ เพราะมันเป็นขั้นตอนที่มักต้องรอคนมากดดู ทำให้ agent ตรวจเองได้ แล้วคุณจะหลุดจากการเป็นคอขวด แต่ถ้าข้ามขั้นตอนนี้ การรัน agent เพิ่มขึ้นมีแต่จะผลิตงานที่ยังไม่ผ่านการตรวจมากองให้คุณอ่านมากขึ้นเท่านั้น

## ระบุเงื่อนไขจบงานตั้งแต่คำสั่งแรก

ใส่คำจำกัดความของคำว่า "เสร็จ" ลงไปใน prompt แรก ด้วยคำพูดแบบไหนก็ได้ที่ชัดเจน:

```text
/poteto-mode add json output to this command. text output stays byte-identical, the json parses, both run against the sample project. show me the evidence.
```

ตอนนี้ agent มีจุดตรวจ 3 ข้อที่รันเช็กได้จริง ไม่ใช่อารมณ์ความรู้สึกที่ต้องเดาใจคุณ เมื่อคำตอบกลับมา มันต้องแนบคำสั่งจริงและผลลัพธ์จริงที่รันได้ หากข้อไหนรันไม่ได้ คำตอบที่ดีจะบอกตรงๆ ว่า "inconclusive" (สรุปไม่ได้) คำตอบที่มั่นใจเต็มเปี่ยมแต่ไม่มีหลักฐานคือสัญญาณอันตราย

เลือกวิธีตรวจให้ตรงกับประเภทของงานที่แก้:

- งานแก้ CLI → รันคำสั่งจริง
- งานแก้ UI → กดเดินตาม flow ที่เปลี่ยนในแอปที่รันจริง และเมื่อต้องตรงกับต้นแบบระดับพิกเซล [Visual parity playbook](../../../skills/poteto-mode/playbooks/visual-parity.md) จะเทียบ diff ภาพหน้าจอกับ baseline ที่ล็อกไว้แทนการกะด้วยสายตา
- งานแก้ parser หรือ migration → รันซ้ำกับข้อมูลตัวอย่างที่บันทึกไว้
- งานปรับประสิทธิภาพ → เทียบ profile ก่อนและหลังแก้
- งานแก้ระบบจัดเก็บข้อมูล → อ่านค่าที่เขียนลงไปกลับขึ้นมาเช็ก

ขอหลักฐานในรูปแบบ artifact ที่คุณเปิดดูเองได้ เช่น test ที่พังก่อนแล้วค่อยผ่าน, วิดีโอก่อน-หลัง, ไฟล์ trace, หรือภาพหน้าจอ ถ้าโค้ดถูก merge ไปแล้ว ให้สั่งรันเช็กเดิมซ้ำบน `main` หลักฐานที่เป็นชิ้นเป็นอันชนะคำอธิบายที่ฟังดูมีเหตุผลเสมอ เพราะคุณจับผิดและท้าทายมันได้โดยไม่ต้องรันงานทั้งหมดซ้ำ

สำหรับ diff ขนาดเล็กที่คุณยังไม่ค่อยไว้ใจ [`/blast-radius`](../../../skills/blast-radius/SKILL.md) จะช่วยค้นหาว่ามันอาจทำส่วนอื่นพังตรงไหนบ้าง มันจะหาข้อเท็จจริงสำคัญข้อเดียวที่ทำให้การแก้นี้ปลอดภัย แล้วพิสูจน์ข้อเท็จจริงนั้นด้วยการรันโค้ดจริง ไม่ใช่การเถียงเอาเหตุผล

## ตรวจตัวเลขที่วัดได้ด้วย `/benchmark-checklist`

ตัวเลขเปรียบเทียบก่อน-หลังคือหลักฐานที่พลาดหลอกตัวเองง่ายที่สุด แคชที่อุ่นอยู่แล้ว, build แบบ debug ที่หลุดมาอยู่ฝั่งเดียว, หรืองานที่ไม่ได้รันอยู่ในช่วงจับเวลาจริง ต่างก็ปั้นตัวเลขความเร็วที่ดูน่าเชื่อถือขึ้นมาได้ทั้งนั้น ก่อนจะเอาตัวเลขไปรายงานหรือตัดสินใจอะไร ให้พิมพ์:

```text
/benchmark-checklist vet the export speedup before it goes in the pr
```

[`/benchmark-checklist`](../../../skills/benchmark-checklist/SKILL.md) จะถาม 7 คำถาม และต้องการหลักฐานจากการรันจริงสำหรับทุกข้อ:

1. อะไรคือตัวจำกัด (limiter) ของตัวเลขนี้ และทำไมมันถึงไม่เร็วขึ้นเป็น 2 เท่า?
2. ทั้งสองฝั่งถูกรันด้วยการตั้งค่าแบบเดียวกับ production จริงหรือไม่?
3. ผลลัพธ์ที่ได้ขัดกับขีดจำกัดทางกายภาพ เช่น disk bandwidth หรือจำนวน core หรือไม่?
4. มีอะไร error หรือคืนค่าผิดพลาดระหว่างรันบ้างไหม?
5. เมื่อสลับรันไปมาหลายรอบ ผลยังทำซ้ำได้ พร้อมค่า median และ range หรือไม่?
6. ตัวเลขนี้ส่งผลต่อเวลา end-to-end ในเส้นทางที่ผู้ใช้รอจริงหรือไม่?
7. งานที่วัดเกิดขึ้นภายในช่วงเวลาที่จับ (timed region) จริงหรือไม่?

คำตัดสินจะออกมาเป็น `faster`, `slower`, `no measurable difference`, หรือ `inconclusive` พร้อมจำนวนรอบที่รัน, ช่วงค่า (range), และตัวจำกัดความเร็ว (limiter) ระบบจะตอบ `inconclusive` ทันทีหากระบุ limiter ไม่ได้ หรือมีฝั่งใดฝั่งหนึ่งไม่ได้ tune เหมือน production ปกติ `/poteto-mode` รัน checklist นี้อยู่แล้วใน Perf issue และ Hillclimb playbook คุณจึงพิมพ์เรียกเองเฉพาะตอนที่วัดผลนอก playbook เหล่านั้น หรือตอนเห็นตัวเลขของใครบางคนดูดีเกินจริง นี่คือรูปธรรมที่ใช้งานได้จริงของหลักการ [Explain the Number](../../../skills/principle-explain-the-number/SKILL.md)

## สร้าง Verification Skill ประจำโปรเจกต์

ข้อ UI ด้านบนซ่อนเงื่อนไขสำคัญข้อหนึ่งไว้ คือ agent ต้องมีวิธีแบบ script เพื่อบังคับขับเคลื่อนแอปของคุณ ถ้าโปรเจกต์คุณมีอยู่แล้วก็ยอดเยี่ยม ถ้ายังไม่มี ให้รัน:

```text
/create-verification-skill
```

[`/create-verification-skill`](../../../skills/create-verification-skill/SKILL.md) จะเข้าไปสำรวจ repository เอง ไม่ได้มานั่งสัมภาษณ์คุณ มันจะไล่ดูเองว่าผู้ใช้กดอะไรได้บ้าง แอปเปิดรันบนเครื่องยังไง ใช้อะไรขับเคลื่อนได้ (ใช้ harness เดิมก่อน หากไม่มีค่อยใช้ browser + CDP, PTY, หรือ HTTP ธรรมดา) หลักฐานแบบไหนที่พิสูจน์พฤติกรรมได้ และรันสองตัวพร้อมกันได้ไหม มันจะถามคุณเฉพาะสิ่งที่หาคำตอบจากโค้ดไม่ได้เท่านั้น

มันจะสร้าง `.cursor/skills/verify-<app>/` ซึ่งเป็นคู่มือสำหรับ agent พร้อมหัวข้อ `Launch`, `Doctor`, `Drive`, `Evidence`, และ `Cleanup` แบบเป๊ะๆ รวมถึงหัวข้อ `Helpers` สำหรับสคริปต์ที่สร้างให้ และโฟลเดอร์ `features/` ที่ทำดัชนี (feature map) ว่าแอปทำอะไรได้บ้างและผลลัพธ์แบบไหนพิสูจน์ว่าฟีเจอร์นั้นทำงานถูกต้อง ในตัว skill มี [ตัวอย่าง feature-map](../../../skills/create-verification-skill/references/feature-map-example/) ที่มี README index และ 1 ไฟล์ต่อ 1 ฟีเจอร์ตาม H2 บังคับทั้ง 4 ข้อ ก่อนส่งมอบ ตัวสร้าง skill จะทดสอบรันจริงครบวงจร 1 รอบ ได้แก่ launch, doctor check, ขับเคลื่อน 1 ฟีเจอร์, เก็บหลักฐาน, cleanup, แล้วตรวจซ้ำว่าหลักฐานยังอยู่ครบหลัง cleanup ถ้าขั้นตอนนี้พัง ห้ามเอาผลลัพธ์นั้นไปใช้

ตั้งแต่นั้นเป็นต้นมา คำว่า "verify it in the app" จะกลายเป็นขั้นตอนที่ agent ตัวไหนใน repo นี้ก็ทำได้ทันทีโดยไม่ต้องมานั่งถามวิธีเปิดรันใหม่ และคุณสามารถเอ่ยชื่อ skill นี้ใน prompt ได้เมื่อต้องการหลักฐานในรูปแบบเฉพาะ:

```text
/poteto-mode build the bulk-archive action. use /verify-<app> to verify your changes and show me a video and screenshots as proof.
```

```text
/poteto-mode repro this with /verify-<app>. if it repros on main, fix it and show me a video as proof.
```

เมื่อ verify skill ใช้งานได้คล่องแล้ว [`/swarm`](../../../skills/swarm/SKILL.md) สามารถแตกงานตรวจทั้งแอปตามรายการใน feature-map แล้วรวมผลเป็นรายงานเดียว หรือสั่งฝูง verifier ช่วยยืนยันผลความเร็วบนกลุ่มตัวอย่างขนาดใหญ่ หรือ fuzz แอปหา regression ก่อน PR จะถูก merge

จงปฏิบัติกับ verification skill เหมือนเป็นโครงสร้างพื้นฐาน (infrastructure) ไม่ใช่ของใช้ครั้งเดียว Commit มันลง repo เพื่อให้คนและ agent ทุกคนในทีมขับเคลื่อนแอปด้วยวิธีเดียวกัน จากนั้นต่อยอดด้วยหลักการ [Build the Lever](../../../skills/principle-build-the-lever/SKILL.md) เมื่อใดที่ agent ต้องเขียนสคริปต์ใช้แล้วทิ้งซ้ำๆ เพื่อมากดปุ่มในแอป ให้สั่งมันสร้าง control CLI เล็กๆ ขึ้นมาให้ verify skill เรียกใช้แทน วิธีนี้ประหยัด token และทำซ้ำได้ทุกครั้ง CLI ที่ agent ใช้งานได้ดีมีลักษณะดังนี้:

- มีคำสั่งที่ประกอบร่างกันได้ (composable) ไม่กี่ตัว แต่ละตัวทำงานจริง แทนที่จะซอยคำสั่งยิบย่อย
- มี `--dry-run` สำหรับคำสั่งที่ทำลายหรือแก้ไขข้อมูล
- มี subcommand ที่ค่อยๆ เปิดเผยความสามารถทีละชั้น ไม่ยัดมาทีเดียวหมด
- ข้อความ error บอกทางแก้ด้วยว่าควรทำอะไรแทน
- มี `--help` ที่ละเอียดอ่านเข้าใจง่าย
- ส่ง output แบบที่เครื่องอ่านได้ เช่น JSON

และในจังหวะเดียวกัน ทำให้การเตรียมสภาพแวดล้อม dev ทำซ้ำได้ง่ายด้วย ทั้ง seed data, test user, และคำสั่งเดียวที่ปลุก environment ขึ้นมาเหมือนเดิมทุกครั้ง

## ดูแลให้ Verification Skill ตรงกับความจริงเสมอ

แอปเปลี่ยนไปเรื่อยๆ และ feature map ก็ล้าสมัยได้ ให้รันคำสั่งนี้อย่างน้อยวันละครั้ง ซึ่งทางที่ดีที่สุดคือตั้งเป็น scheduled automation จะได้ไม่ต้องคอยจำ:

```text
/maintain-verification-skill
```

[`/maintain-verification-skill`](../../../skills/maintain-verification-skill/SKILL.md) จะตรวจสอบ skill ที่สร้างไว้ โดยส่งตัวอ่านโค้ดแบบ read-only 1 ตัวต่อ 1 ฟีเจอร์ไปตรวจขนานกัน จากนั้นรันทดสอบจริงกับทุกฟีเจอร์ในแผนที่ ผลลัพธ์จะจบลงด้วย 1 ใน 3 สถานะเท่านั้น คือ `clean` หมายถึงครอบคลุมครบและไม่ต้องแก้อะไร, `changed` หมายถึงเปิด 1 PR เพื่อแก้ไขเฉพาะในโฟลเดอร์ของ verification skill ที่พิสูจน์แล้ว, และ `blocked` พร้อมระบุตัวขวาง มันจะไม่มีวันไปแก้โค้ดของตัวแอป และหากการรันจริงไปเจอ bug/regression ของแอป มันจะรายงานว่าเจอ bug แทนที่จะไปแก้เอกสารเพื่อกลบเกลื่อน

## พิสูจน์คุณสมบัติด้วย Formal Verification Skill

Verification skill พิสูจน์เส้นทางที่เราสั่งกดทดสอบ แต่บั๊กบางตัวซ่อนอยู่ในเส้นทางที่ไม่มีใครกดถึง เช่น retry สองรอบที่ซ้อนทับกัน, lock ที่หมดอายุกลางคันระหว่างเขียนข้อมูล, หรือ state change ที่มาถึงผิดลำดับ test ทั่วไปมักเอื้อมไม่ถึงเคสเหล่านี้ สำหรับโค้ดส่วนที่บั๊กแบบนี้สร้างความเสียหายสูง ให้รัน:

```text
/create-formal-verification-skill
```

[`/create-formal-verification-skill`](../../../skills/create-formal-verification-skill/SKILL.md) จะเลือกเป้าหมายจากโค้ดเอง นั่นคือ "คำสัญญาที่โค้ดให้ไว้" จุดที่หากพังจะกระทบผู้ใช้หนักและ test ทั่วไปไม่ค่อยเจอเคสพัง มันจะเลือกจุดที่คุ้มค่าที่สุด ไม่ใช่จุดที่พิสูจน์ง่ายที่สุด หรือคุณจะชี้จุด/บั๊กให้เริ่มตรงนั้นก็ได้:

```text
/create-formal-verification-skill the job lease and retry logic. a job must never run twice at once.
```

คำถามจะเป็นตัวเลือกเครื่องมือ หากเป็นเรื่องเหตุการณ์เกิดขึ้นผิดลำดับได้ไหม จะเหมาะกับ model checker บนแบบจำลองขนาดเล็กของดีไซน์ ซึ่ง TLA+ คือค่าเริ่มต้นไม่ว่าโปรเจกต์จะเขียนด้วยภาษาใด หากเป็นเรื่องโค้ดทำงานถูกกับทุก input หรือไม่ จะเหมาะกับ verifier ที่รันบนโค้ดจริง และถ้าภาษานั้นไม่มี verifier ให้ใช้ agent จะบอกตรงๆ แล้วหันไปทดสอบโค้ดจริงด้วย input ที่สุ่มสร้างขึ้นแทนการเขียนแบบจำลองปลอมขึ้นมาเอง สำหรับคุณสมบัติที่ต้องเป็นจริงกับทุกขนาดข้อมูลอาจต้องใช้การพิสูจน์เชิงคณิตศาสตร์ (proof) โดย agent จะบอกคุณว่าเลือกเครื่องมือไหนและเพราะอะไร

ระบบจะพิสูจน์คุณสมบัติ 1 ข้อ และต้องแสดงให้เห็นว่าคุณสมบัตินั้น **พังจริง** บนโค้ดเวอร์ชันที่จงใจทำให้เสีย เพราะตัวตรวจที่ไม่เคยเห็นมันฟ้อง error เลยพิสูจน์อะไรไม่ได้ ถ้าโค้ดปัจจุบันละเมิดคุณสมบัตินั้นอยู่แล้ว คุณจะได้ counterexample เป็นลำดับขั้นตอนสั้นๆ ในภาษาโค้ดของคุณ คุณสมบัติ (property) จะถูกคงไว้ตามเดิมเพื่อให้ข้อค้นพบยังคงเป็นข้อค้นพบ โค้ดตัวแอปจะไม่ถูกแก้จนกว่าคุณจะสั่ง

มันจะสร้าง skill ประจำโปรเจกต์ที่บอก agent ตัวถัดไปได้ว่าการแก้โค้ดครั้งนี้แตะส่วนที่ผ่านการพิสูจน์หรือไม่ ต้องรันตรวจด้วยคำสั่งไหนในบรรทัดเดียว และวิธีแยกแยะบั๊กจริงออกจากความผิดพลาดในการสร้างแบบจำลอง ก่อนส่งมอบ ตัวสร้างจะลองรัน skill นั้นกับโค้ดชั่วคราวที่จงใจทำให้ละเมิด property และตัวตรวจต้องจับได้จริง บทสรุปส่งมอบจะระบุชัดเจนว่าพิสูจน์อะไร ด้วยเครื่องมือไหน ขอบเขต (bounds) แค่ไหน เจออะไรบ้าง และ **ไม่ครอบคลุมอะไรบ้าง** การผ่านหนึ่งครั้งหมายถึงผ่านในแบบจำลองหรือขอบเขตที่ตั้งไว้ ไม่ใช่ทั้งระบบ

skill นี้ยังบันทึกไว้ด้วยว่าตัวตรวจแต่ละตัวครอบคลุมโค้ดส่วนไหนและตรงกับ commit ล่าสุดใด เพราะการ merge หรือ refactor ที่ข้ามขั้นตอนนี้ไป อาจทำให้ตัวตรวจยังรายงานว่าผ่านทั้งที่มันกำลังตรวจคำอธิบายของโค้ดเก่าที่ถูกลบทิ้งไปแล้ว หลังจากเกิดการเปลี่ยนแปลงเหล่านั้น ให้รัน [`/maintain-formal-verification-skill`](../../../skills/maintain-formal-verification-skill/SKILL.md) ระบบจะอัปเดตตัวตรวจตามโค้ดล่าสุด รันใหม่ แสดงว่าแต่ละตัวยังจับความพังได้ และแยกให้คุณดูว่าความล้มเหลวที่เจอเกิดจากตัวตรวจล้าสมัย (drift) หรือบั๊กในโค้ดจริง

## แสดงพฤติกรรมเป็นแผนภาพ Statechart

counterexample ในภาษาของ model อาจทำให้คุณเชื่อได้ แต่ PM หรือดีไซเนอร์ที่เป็นเจ้าของพฤติกรรมนั้นต้องเห็นมันในภาษาของพวกเขา ให้รัน:

```text
/statechart what the user sees when they edit a note offline
```

[`/statechart`](../../../skills/statechart/SKILL.md) จะวาดแผนภาพ Mermaid statechart แสดงสิ่งที่ผู้ใช้มองเห็น โดยสร้างขึ้นจากแบบจำลอง TLA+ เพื่อไม่ให้รูปภาพกับแบบจำลองที่ถูกตรวจคลาดเคลื่อนจากกัน กฎฝั่งผู้ใช้งาน (เช่น "คุณจะไม่มีวันเห็นสถานะ Synced ในขณะที่กำลังออฟไลน์") จะกลายเป็น invariants แผนภาพจะมาร์กทุก state ที่ละเมิดกฎ และรายงานจะชี้เส้นทางที่สั้นที่สุดในการเดินไปเจอจุดพังนั้นด้วยภาษาของผู้ใช้งาน ก่อนส่งมอบ agent จะจำลองเส้นทางบั๊กทุกจุดบนโค้ดจริง เพื่อให้แน่ใจว่าความผิดพลาดของโมเดลจะไม่หลุดไปถึงคนอ่านในคราบบั๊ก

## เปิด PR

```text
/poteto-mode open the pr. small ordered commits, evidence in the description.
```

[Opening a PR playbook](../../../skills/poteto-mode/playbooks/opening-a-pr.md) ทำงานจาก worktree, rebase งานให้เป็น commit เล็กๆ ที่เรียงลำดับอ่านง่ายและพร้อม merge, ทำความสะอาด diff, เขียนสรุปสไตล์ briefing ที่อ่านจบใน 1 นาทีใส่ในคำอธิบาย PR, แล้วเปิด PR แบบพร้อมรีวิว การแบ่ง PR ต่อเรียงกันเป็นชั้นเล็กๆ (stacked follow-ups) ดีกว่ากิ่งเดียวที่บวมโตขึ้นเรื่อยๆ

## พา PR ไปจนพร้อม Merge ด้วย Babysit

ทันทีที่เปิด PR มันก็เริ่มสะสมตัวขวางทาง ทั้ง check พัง, ความเห็นจาก reviewer, และ branch หลักขยับหนี ยกงานจุกจิกพวกนั้นให้ [Babysit playbook](../../../skills/poteto-mode/playbooks/babysit.md):

```text
/poteto-mode babysit this pr. get it green.
```

Babysit จะเฝ้าดู PR ผ่านตัว watcher ในชุดเครื่องมือบน GitHub (หรือ Origin CLI เมื่อมีใช้) และจัดการตัวขวางตามลำดับ: conflict ก่อน ตามด้วย review thread แล้วค่อย CI มันจะ **ไม่มีวัน** rebase หรือ force-push เอง หากเจอ conflict หรือฐาน branch ล้าสมัย มันจะกลับมาแจ้งคุณพร้อมระบุ branch ที่ต้อง rebase ส่วนการคัดแยกคอมเมนต์จะใช้ท่าทีที่ตั้งข้อสงสัยไว้ก่อน (skeptical) เพราะทั้งคนและบอทมักปนข้อจับผิดจริงเข้ากับความเห็นจุกจิกไร้สาระในรายการเดียวกัน จุดที่พังจริงจะถูกแก้ ส่วน noise จะถูกโต้แย้งพร้อมหลักฐานหักล้างใน thread นั้น ถ้าคุณแค่อยากเช็กสถานะ ไม่ต้องเปิด loop แค่ถามสั้นๆ Babysit จะตอบให้โดยไม่รันวน:

```text
/poteto-mode check on pr 123. anything outstanding?
```

Babysit จะหยุดอยู่ที่จุดพร้อม merge (`merge-ready`) มันจะไม่มีวันกด merge เอง แม้ทุกอย่างจะเขียวหมดแล้ว เพราะการ merge เป็นอีกการตัดสินใจหนึ่งต่างหาก

## นำ Stack ขึ้น Merge ด้วย Shipping

ตัวเช็กขึ้นสีเขียวไม่ได้แปลว่าปลอดภัย เมื่อพร้อมจะเอาโค้ดลง main ให้สั่ง:

```text
/poteto-mode land the stack.
```

[Shipping playbook](../../../skills/poteto-mode/playbooks/shipping.md) จะตรวจพิสูจน์ PR ทุกตัวแยกกันอย่างอิสระก่อนจะเตรียมสั่ง merge โดยส่ง agent ตัวใหม่เอี่ยม 1 ตัวต่อ 1 PR ไปพิสูจน์พฤติกรรมจริง และ agent ที่เป็นคนตัดสินต้องไม่ใช่ตัวเดียวกับที่เขียนโค้ด จากนั้น Shipping จะสั่ง merge เฉพาะแถว PR ต่อเนื่องตั้งแต่ล่างสุดที่ผ่านการตรวจครบแล้วเท่านั้น ทีละ PR ผ่าน GitHub เป็นค่าเริ่มต้น (หรือ Origin เมื่อมี CLI) และรายงาน PR แรกที่ทำให้โซ่ขาด ส่วน PR ที่ผ่านการตรวจแล้วแต่วางซ้อนอยู่เหนือ PR ที่ยังไม่ผ่านจะต้องรอ เพราะการ merge ข้ามไปจะเป็นการดึงช่องโหว่ข้างล่างลงมาด้วย

## สรุปท้ายบท

- **แก่นของบทนี้:** ทำให้ AI พิสูจน์งานตัวเองกับของจริงได้ แล้วคุณจะไม่ใช่คอขวดของทีมอีกต่อไป
- **เครื่องมือพิสูจน์ 4 ระดับ (จากเร็วไปลึก):**
  1. **Real-world check & `/verify-<app>`** → ขับเคลื่อนแอปจริงและเก็บหลักฐาน (ภาพ/วิดีโอ/ค่าจริง)
  2. **`/benchmark-checklist`** → สอบสวน 7 ข้อก่อนเชื่อตัวเลขความเร็ว
  3. **`/blast-radius`** → หาและพิสูจน์จุดที่อาจพังนอก diff
  4. **`/create-formal-verification-skill` & `/statechart`** → ใช้ TLA+/model checker จับบั๊ก concurrency หรือลำดับเหตุการณ์ที่ test ทั่วไปไม่ถึง
- **แยก PR Lifecycle ชัดเจน:** `Opening a PR` (จัด commit + เปิด) → `Babysit` (เคลียร์ thread + CI แต่ไม่ merge) → `Shipping` (ตรวจซ้ำอิสระทีละ PR แล้วค่อย land ต่อเนื่อง)
