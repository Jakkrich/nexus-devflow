# บทที่ 3: ทำความเข้าใจโค้ดก่อนแก้

การแก้โค้ดที่คุณยังไม่เข้าใจคือวิธีที่บั๊กถดถอย (regression) แบบแอบซ่อนหลุดขึ้น production ซึ่งเป็นจริงทั้งกับคนและกับ agent ปกติ agent มักพังด้วย 2 สาเหตุ คือตีความสิ่งที่คุณต้องการผิด หรือไม่มีบริบทพอที่จะทำงานให้ถูก เรื่องแรกแก้ได้ด้วย [สิ่งที่ควรใส่ใน prompt](./02-poteto-mode.md#ใน-prompt-ควรใส่อะไรบ้าง) ส่วนบทนี้แก้เรื่องที่สอง

pstack มีประตูเข้า 4 ทาง `/how` อธิบายว่าโค้ดทำงานอย่างไรในตอนนี้ `/why` ขุดหาเหตุผลว่าทำไมมันถึงถูกสร้างมาหน้าตาแบบนี้ `/teach` ผสมทั้งสองอย่างเป็นคำอธิบายชุดเดียว และ `/recall` ดึงความจำจากบริบทล่าสุดของคุณในเรื่องนั้นขึ้นมาใหม่ ทั้งสี่คำสั่งยังบังคับให้ agent อธิบายตัวเองด้วยภาษาที่คุณตรวจสอบได้ นั่นคือวิธีคุม agent ที่อาจรู้จักโค้ดมากกว่าตัวคุณเอง

## เริ่มด้วยการสำรวจแบบ Read-only

เมื่อยังไม่รู้ต้นตอของปัญหา ให้ขอ "ข้อค้นพบ" อย่าเพิ่งขอ "การแก้":

```text
/poteto-mode investigate why background jobs time out every few hours. give me what we know, what data you used, and your best hypotheses. don't change any code yet.
```

วลี "don't change any code yet" จะส่งงานนี้เข้า [Investigation playbook](../../../skills/poteto-mode/playbooks/investigation.md) มันจะไล่ตามโค้ด เรียก `/why` เมื่อมีคำถามเรื่องเจตนาเดิม แล้วส่งคำอธิบายพร้อมแหล่งอ้างอิงกลับมา ถ้าเป็นการเลือกระหว่างหลายทางเลือก จะได้คำแนะนำพร้อมตารางเปรียบเทียบข้อดี-ข้อเสีย การถามว่า "what data you used" บังคับให้ agent แยกหลักฐานจริงออกจากสิ่งที่มันเดาเอาเอง เมื่อข้อค้นพบชี้ไปยังจุดที่ต้องแก้ ค่อยเปิดการแก้เป็นงานใหม่แยกต่างหาก

## แกะรอยพฤติกรรมด้วย `/how`

```text
/how do we dedupe notifications? is there an n+1 when we look up subscribers?
```

ถามคำถามที่คุณสงสัยจริงๆ ได้เลย [`/how`](../../../skills/how/SKILL.md) จะอ่านโค้ดแล้วตอบในระดับเดียวกับ senior engineer ที่กำลัง onboard คุณเข้าสู่ระบบย่อยนั้น พร้อม flow การทำงานจริง type สำคัญ และจุดที่ดูเผินๆ แล้วมองไม่เห็น โดยมันจะส่ง read-only subagent หนึ่งตัวไปสำรวจโค้ดแล้วเขียนคำอธิบายกลับมา

## ขุดประวัติศาสตร์ด้วย `/why`

```text
/why was the retry limit set to five? does the reason still hold?
```

[`/why`](../../../skills/why/SKILL.md) ตอบจากหลักฐานบันทึก ไม่ใช่แค่จากโค้ดปัจจุบัน มันจะอ่าน commit และบทสนทนาใน PR ที่สร้างโค้ดนั้น รวมถึงการแก้ไขถัดๆ มา และค้นแหล่งอื่นต่อหากร่องรอยใน git ยังบาง คำตอบจะอ้างอิงสิ่งที่ผู้เขียนเดิมบันทึกไว้ แยกแยะชัดเจนว่าจุดไหนคือการอนุมาน (inference) ของตัว agent เอง และบอกตรงๆ ว่าอะไรที่บันทึกไม่เคยเขียนไว้ เพราะคำตอบว่า "ไม่มีใครเคยจดเหตุผลไว้" ก็เป็นข้อเท็จจริงที่มีค่าเช่นกัน

สองคำสั่งนี้ประกอบกันได้ลงตัว `do why first then how` เป็นคำสั่งที่ดีมากเมื่อคุณสงสัยว่าเรื่องราวในอดีตจะช่วยอธิบายความยุ่งเหยิงตรงหน้าได้

## ทำความเข้าใจให้ถึงแก่นด้วย `/teach`

```text
/teach me how this PR changes retries. convince me it fixes the cause and not the symptom.
```

[`/teach`](../../../skills/teach/SKILL.md) มีไว้ใช้เมื่อคำสรุปสั้นๆ ยังไม่พอ มันจะรัน `/how` และ `/why` (สำหรับงานเล็กอาจรันแค่ตัวเดียว) แล้วถักทอข้อมูลที่ได้ออกมาเป็นคำอธิบายภาษาคน ที่ค่อยๆ ต่อภาพขึ้นทีละแผนภาพ กรอบคำถามแบบ "convince me..." (ทำให้ฉันเชื่อหน่อยว่า...) เป็นเทคนิคที่น่าเก็บไว้ใช้ซ้ำ เพราะมันเปลี่ยนคำอธิบายให้เป็นข้อโต้แย้งที่คุณทดสอบจับผิดได้ แทนที่จะเป็นแค่ทัวร์ชมโค้ด

คำสั่งนี้ใช้ไล่เบี้ยการตัดสินใจของตัว agent เองได้ด้วย:

```text
/teach me why you implemented it this way and not with a queue. what did you trade off, and why?
```

การสอนช่วยให้ agent เก่งขึ้นพอๆ กับช่วยคุณ เพราะ agent ที่ต้องอธิบายงานของตัวเองถูกบังคับให้อ่านโค้ดจริงและอ้างหลักฐานทุกประโยค แทนที่จะพูดสรุปอย่างมั่นใจแล้วข้ามไป

## กู้บริบทของคุณเองด้วย `/recall`

```text
/recall catch me up on the export work from last week
```

[`/recall`](../../../skills/recall/SKILL.md) จะขุดคุ้ยประวัติแชทล่าสุดของคุณรวมกับบันทึกส่วนกลาง (issues, การแก้ก่อนหน้า, error ที่ยังโผล่อยู่) แล้วส่งสรุปสั้นๆ กลับมาว่าตอนนี้งานถึงไหนและต้องทำอะไรต่อ แชทเก่าๆ ของคุณเก็บบริบทที่ agent ตัวใหม่ไม่มี ดังนั้นเมื่อจะกลับมาลุยงานเก่าต่อ ให้โหลดความจำขึ้นมาก่อน แล้วค่อยส่งข้อมูลใหม่ให้มัน:

```text
/recall my work on the virtualized list from yesterday, then read this bug report.
```

แต่ถ้าคุณต้องการกลับไปสานต่อแชทใดแชทหนึ่งโดยเฉพาะ อันนั้นให้ใช้ Session pickup playbook ด้านล่าง ไม่ใช่ `/recall`

## รับช่วงต่อจากงานค้างด้วย Session pickup

เมื่อ agent ตัวอื่น (หรือตัวคุณเองเมื่อสัปดาห์ก่อน) ทำ branch หนึ่งค้างไว้กลางทาง:

```text
/poteto-mode take over this branch. read the decision log, figure out what's done, and continue from there. don't redo finished work.
```

[Session pickup playbook](../../../skills/poteto-mode/playbooks/session-pickup.md) จะยึดร่องรอยเดิมเป็นหลักฐานอ้างอิง มันจะประกอบภาพสถานะของ branch และการตัดสินใจที่ผ่านมา ระบุจุดที่ต้องทำต่อ และตรวจทานสมมติฐานที่รับช่วงมาเทียบกับเป้าหมายตั้งต้น แทนที่จะไปรื้อทำใหม่ทั้งหมดตั้งแต่ศูนย์

**กับดัก:** อย่าข้าม skill ในบทนี้เพราะคิดว่า "เดี๋ยว agent ก็อ่านโค้ดเองอยู่ดี" agent ที่กระโดดเข้าไปแก้โค้ดโดยไม่มีแบบจำลองการทำงานในหัวมักจะไปแก้แค่อาการปลายเหตุในจุดแรกที่ดูน่าจะใช่ การรัน `/how` ก่อนถูกกว่าการตามแก้บั๊กรอบที่สองเสมอ

## สรุปท้ายบท

- **แก่นของบทนี้:** ทำความเข้าใจโค้ดและประวัติศาสตร์ให้ขาดก่อนลงมือแก้ — แยกเฟส "สืบสวน" ออกจากเฟส "ลงมือแก้" เสมอ
- **เลือกใช้เครื่องมือให้ถูกจังหวะ:**
  - อยากรู้ว่า **ระบบทำงานยังไงตอนนี้** → `/how`
  - อยากรู้ว่า **ทำไมถึงเขียนมาแบบนี้** → `/why`
  - อยากให้ **อธิบายและโน้มน้าวด้วยหลักฐานทีละขั้น** → `/teach` (`convince me...`)
  - อยาก **ดึงบริบทจากแชทเก่า** → `/recall` หรือสานต่อ branch ค้างด้วย Session pickup
- **ข้อคิดสำคัญ:** การสั่ง `don't change any code yet` ในตอนสำรวจช่วยกันไม่ให้ agent รีบแปะโค้ดแก้ปลายเหตุก่อนเจอต้นตอจริง
