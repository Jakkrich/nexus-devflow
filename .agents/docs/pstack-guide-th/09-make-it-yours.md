# บทที่ 9: ปรับแต่งให้เข้ากับสไตล์ของคุณ

`poteto-mode` เป็นสไตล์ของคนคนหนึ่งเท่านั้น แต่ playbook, ระบบ route, และบทบาทโมเดลที่อยู่ข้างใต้สามารถใช้งานร่วมกับสไตล์ของคุณเองได้ดีไม่แพ้กัน บทนี้ครอบคลุมการสร้างโหมดส่วนตัว, การถอดบทเรียนจาก session, การแก้ repo เพื่อไม่ให้ agent ทำพลาดเรื่องเดิมซ้ำ, การเขียน skill เฉพาะทาง, และการทดสอบ skill ที่แก้ก่อนนำไปใช้งานจริง

เริ่มต้นให้เล็กกว่าที่คิด คุณไม่จำเป็นต้องมี skill เยอะตั้งแต่วันแรก หรือแม้แต่ plugin ทั้งชุดนี้ แค่สั่งงานด้วยภาษาธรรมดา สังเกตจุดที่ agent พลาด แล้วค่อยเพิ่ม skill หรือตัวเช็กเมื่อความผิดพลาดแบบเดิมโผล่มาซ้ำเป็นครั้งที่สอง

## สร้างโหมดส่วนตัวของคุณด้วย `/automate-me`

```text
/automate-me
```

คุณไม่ต้องนั่งบรรยายสไตล์ตัวเอง เพราะ [`/automate-me`](../../../skills/automate-me/SKILL.md) จะไปอ่านออกมาจากประวัติการทำงานของคุณเอง มันจะขุด transcript ล่าสุดใน workspace ที่เปิดอยู่เพื่อหาความชอบที่เกิดซ้ำ ทั้งวิธีตอบกลับ, การมอบหมายงาน, การพิสูจน์งาน, โค้ด, ภาษา, และขั้นตอนการทำงาน แล้วหันมาถามยืนยันกับคุณว่า pattern ไหนคือตัวตนของคุณจริงๆ จากนั้นจะร่าง `.cursor/skills/<your-name>-mode/SKILL.md` ผ่าน `create-skill` ของ Cursor, ส่งไปขัดเกลาด้วย [`/unslop`](../../../skills/unslop/SKILL.md), และเปิด PR จาก worktree เพื่อให้คุณรีวิวเหมือนการแก้โค้ดปกติ

รันซ้ำได้ทุกเมื่อที่นิสัยการทำงานของคุณเปลี่ยนไป:

```text
/automate-me update my mode skill with everything since its last edit
```

โหมดอัปเดตจะขุดเฉพาะประวัติที่เกิดขึ้นหลังการแก้ skill ครั้งล่าสุด โดยจะคงกฎที่คุณไม่ได้ขัดแย้งไว้ ปรับปรุงกฎที่มีหลักฐานใหม่ และเพิ่มหัวข้อใหม่เฉพาะ pattern ที่เพิ่งเกิดขึ้น

## เก็บบทเรียนหลังจบงานด้วย `/reflect`

ทันทีที่จบงานซึ่งให้บทเรียนสำคัญกับคุณ ให้รัน:

```text
/reflect that took way too long. capture what we learned so the next run doesn't repeat it.
```

[`/reflect`](../../../skills/reflect/SKILL.md) จะอ่าน transcript แล้วคัดเก็บเฉพาะบทเรียนที่จะเปลี่ยนวิธีทำงานของ agent ในอนาคต จากนั้นจัดข้อเสนอเป็น 3 กลุ่มคือ `Accepted`, `Rejected`, และ `Backlog` แล้วรอให้คุณอนุมัติก่อนจะไปแก้ไข skill ใดๆ อนุมัติเฉพาะข้อที่จะเปลี่ยนการตัดสินใจในอนาคตได้จริง เหตุการณ์แปลกประหลาดแค่ครั้งเดียวเป็นแค่เรื่องเล่า ไม่ใช่กฎ

## แก้สภาพแวดล้อมด้วย `/correct`

เมื่อคุณต้องคอยแก้ความผิดพลาดเรื่องเดิมซ้ำแล้วซ้ำเล่าให้ agent สิ่งที่ต้องแก้คือตัว repo ไม่ใช่การเขียน prompt รอบหน้าให้ยาวขึ้น จัดลำดับตัวเลือกตามความทนทานในการป้องกัน:

1. **ทำให้ความผิดพลาดเกิดขึ้นไม่ได้เลย** ด้วยสถาปัตยกรรมหรือโครงสร้างข้อมูลที่ดีกว่าเดิม
2. **บล็อกด้วย type** หรือด้วย lint / CI check ที่ข้อความ error บอกวิธีแก้ที่ถูกต้องไว้ด้วย
3. **ดักจับด้วย test**
4. **เขียนไว้เป็นเอกสารหรือ agent rule** — ข้อนี้มาเป็นอันดับสุดท้าย เพราะเวลา agent ข้าม rule ไป ไม่มีอะไรพังฟ้องขึ้นมา

การรอให้คนมานั่งตรวจเจอใน review ไม่อยู่ในรายการด้วยซ้ำ เพราะการที่คนต้องคอยจับผิดเรื่องเดิมในทุก PR คือปัญหาที่ระบบนี้สร้างมาเพื่อกำจัด [`/correct`](../../../skills/correct/SKILL.md) จะเป็นตัวลงมือแก้ให้:

```text
/correct agents keep calling the database client directly instead of going through the repository layer
```

มันจะอ่าน commit ล่าสุด, การ revert, คอมเมนต์ใน PR review, และ comment ในโค้ดที่อธิบายการเขียนอ้อม (workaround) แล้วจัดกลุ่มความผิดพลาดออกเป็นหมวด (class) หมวดหนึ่งจะถูกนับก็ต่อเมื่อเกิดขึ้นแล้วอย่างน้อย 2 ครั้ง จากนั้นจะแก้หมวดที่พบบ่อยที่สุดทีละ 1 commit โดยเลือกระดับป้องกันที่สูงที่สุดเท่าที่ทำได้ และต้องพิสูจน์ว่าตัวเช็กใหม่นั้นฟ้องพังจริงเมื่อเจอความผิดพลาดเก่าในอดีต นอกจากนี้มันยังรักษาตารางในไฟล์คำสั่งของ agent เพื่อจับคู่กฎแต่ละข้อกับตัวบังคับใช้ (enforcer) ดังนั้นกฎไหนที่ไม่มีอะไรบังคับใช้เลยจะโผล่ขึ้นมาให้เห็นชัดหากเกิดซ้ำ ในคำตอบจะสรุปแต่ละหมวดพร้อมหลักฐาน ระดับที่เลือกใช้ และเหตุผลที่ระดับสูงกว่าใช้ไม่ได้

ถ้าอยากให้มันหาจุดพลาดซ้ำจากประวัติทั้งหมดเอง ให้รัน `/correct` เปล่าๆ โดยไม่ต้องใส่คำอธิบาย `/reflect` กับ `/correct` แบ่งงานกันชัดเจน: `/reflect` พัฒนา skill จากหนึ่ง session ส่วน `/correct` ปรับเปลี่ยนตัว repo เพื่อปิดทางไม่ให้ความผิดพลาดหมวดนั้นกลับมาอีก จับคู่กับ `/architect` ได้เมื่อทางแก้ต้องสร้างขอบเขตโมดูลใหม่ (ดูตัวอย่าง prompt ที่รันทั้งสองอย่างพร้อมกันได้ทั้ง repo ใน [บทที่ 7: รันหลายโปรเจกต์ขนานกัน](./07-overnight.md#รันหลายโปรเจกต์ขนานกัน))

## เขียน Skill เฉพาะทางขึ้นมาเอง

เมื่อคุณมี workflow ที่รู้ชัดแล้วว่าอยากบันทึกเก็บไว้ใช้:

```text
/poteto-mode write a skill for verifying database migrations in this repo
```

การเขียน skill จะเข้าสู่ [Authoring or modifying a skill playbook](../../../skills/poteto-mode/playbooks/authoring-a-skill.md) ซึ่งส่งผ่าน `create-skill` ของ Cursor ตรวจความถูกต้องของ frontmatter และลิงก์ทั้งหมด แล้วส่งต่อผ่าน Opening a PR playbook ข้อความที่เขียนให้ agent อ่านมีมาตรฐานสูงกว่าข้อความให้คนอ่าน เพราะประโยคที่ไม่เป็นประโยชน์หนึ่งประโยคจะกลายเป็นคำสั่งที่ agent ในอนาคตทำตามอย่างซื่อสัตย์ ให้ playbook คุมมาตรฐานนั้นแทนการเขียน `SKILL.md` ด้วยมือเปล่า

มี 2 กรณีพิเศษที่มีตัวสร้างแยกของตัวเอง คือ skill ที่ต้องขับเคลื่อนแอปจริงเพื่อพิสูจน์พฤติกรรม (ใช้ [`/create-verification-skill`](../../../skills/create-verification-skill/SKILL.md) และ [`/maintain-verification-skill`](../../../skills/maintain-verification-skill/SKILL.md)) และ skill ที่ตรวจคุณสมบัติของโค้ดด้วย model checker หรือ proof (ใช้ [`/create-formal-verification-skill`](../../../skills/create-formal-verification-skill/SKILL.md) และ [`/maintain-formal-verification-skill`](../../../skills/maintain-formal-verification-skill/SKILL.md)) ดูรายละเอียดทั้งสองแบบใน [บทที่ 6](./06-verify-and-ship.md#พิสูจน์คุณสมบัติด้วย-formal-verification-skill)

## เขียนเอกสารให้ได้มาตรฐานด้วย `/technical-writing`

ไม่ได้มีแค่ skill เท่านั้นที่เป็นงานเขียนที่คุณต้องส่งมอบ สำหรับ docs, RFCs, README, คำอธิบาย PR และข้อความ commit:

```text
/technical-writing review the readme changes
```

[`/technical-writing`](../../../skills/technical-writing/SKILL.md) ใช้มาตรฐานเป็นชั้นๆ เป้าหมายคือข้อความที่วิศวกรที่กำลังเหนื่อยล้าสามารถเข้าใจได้ตั้งแต่การอ่านรอบแรก มันจะเลือกโหมดของเอกสารก่อน (`tutorial`, `how-to`, `reference`, หรือ `explanation`) แล้วตรวจไล่ทีละประโยค: ใครทำอะไร, หนึ่งความคิดต่อหนึ่งประโยค, ไม่มีประโยคไหนตีความได้สองแง่ ใช้สั่งรีวิวสิ่งที่คุณหรือ agent เพิ่งเขียน หรือระบุชื่อมันตั้งแต่ต้นตอนสั่งให้เขียนเอกสาร

## ทดสอบการแก้ Skill แบบ Blind Eval

การแก้ 1 skill ส่งผลกับทุก session ในอนาคต จงทดสอบมันเหมือนการทดลองทางวิทยาศาสตร์ และใช้มาตรฐานเดียวกันเมื่อนำ skill ของคนอื่นมาใช้ ตรวจให้แน่ใจว่ามันทำให้ agent ทำงานของคุณได้ดีขึ้นจริงๆ ก่อนจะเก็บไว้ใช้

```text
/poteto-mode run the eval playbook on this skill change. same task for both variants, candidates stay blind.
```

เมื่อมี skill ตัวหนึ่งพลาดเป้าอยู่เรื่อยและคุณรู้ว่ามันควรทำอะไร ให้แก้และประเมินผลในงานเดียวกัน:

```text
/poteto-mode update the review skill so it flags missing migrations, and eval the change.
```

การสั่ง eval ตั้งแต่ต้นช่วยคุมความซื่อสัตย์ของการแก้ไข การแก้จากความผิดพลาดใน session เดียวมักทำให้ skill เกิดอาการ overfit กับ session นั้น และพอแก้สะสมไปหลายรอบ skill ก็เพี้ยนไปไกล การ eval จะจับอาการเพี้ยนนี้ได้ก่อนที่มันจะถูก merge

[Eval playbook](../../../skills/poteto-mode/playbooks/eval.md) สร้างขึ้นมาเพื่อรับมือความล้มเหลวรูปแบบเดียว คือ **observer effect** (agent ที่รู้ตัวว่ากำลังถูกทดสอบจะเปลี่ยนพฤติกรรม) ดังนั้นผู้เข้าแข่งขันจะได้รับโจทย์ที่ดูเหมือนงานปกติในโฟลเดอร์ที่ล้างร่องรอยออกหมด ไม่มีคำว่า "eval" หรือ "candidate" และไม่รู้ถึงการมีอยู่ของอีกฝั่ง จากนั้นกรรมการตัวเดียวจะให้คะแนนผลลัพธ์ทั้งหมดภายใต้ป้ายชื่อที่เป็นกลาง และการทำตามลำดับขั้นตอนจะถูกตรวจจากไฟล์ที่ตัวผู้เข้าแข่งขัน **เปิดอ่านจริง** ไม่ใช่จากสิ่งที่มันอ้างในรายงานว่าได้อ่านแล้ว

จงอ่านผลลัพธ์ทุกชิ้นด้วยตาตัวเองก่อนยอมรับคำตัดสินของกรรมการ ถ้าคุณเห็นต่างจากกรรมการ ให้สงสัยเกณฑ์ rubric ก่อนที่จะสงสัยวิจารณญาณของตัวเอง

## สร้าง UI สั่งบอทด้วย `/make-bot-ui`

มี skill เฉพาะทางอีกหนึ่งตัวสำหรับผู้ใช้ Grok Bot คือ [`/make-bot-ui`](../../../skills/make-bot-ui/SKILL.md) ที่สร้างหน้าเว็บขนาดเล็กซึ่งปุ่มต่างๆ ใช้ปลุก bot ผ่าน webhook routine ได้ เช่น ปัดดูคิวงานที่ต้องรีวิวแล้วทุกการปัดจะสั่งให้ bot จัดการรายการนั้น ตัวเซิร์ฟเวอร์บนเครื่องของคุณเป็นตัวถือ sender key ของ webhook ทำให้คีย์ไม่เคยหลุดไปถึงเบราว์เซอร์หรือหน้าแชท นอกจากนี้ตัว skill ยังครอบคลุมวิธีเปิดหน้าเว็บนั้นผ่าน Tailscale ด้วย

**กับดัก:** อย่าแก้ skill กลางคันระหว่างทำงานหลักเพียงเพราะมันดื้อ แก้มันแยกเป็น PR ของตัวเองแล้วเดินหน้างานหลักต่อ การแก้ skill ที่ติดปนมากับ PR ฟีเจอร์จะหายไปจากสายตาคนรีวิวและประเมินผลไม่ได้เลย

## สรุปท้ายบท

- **แก่นของบทนี้:** เริ่มจากเล็กๆ แล้วค่อยเปลี่ยนบทเรียนที่เจ็บซ้ำให้เป็นระบบป้องกันถาวร
- **แยกเครื่องมือเรียนรู้ให้ถูกคู่:**
  - `/automate-me` = สกัดสไตล์ของคุณจากประวัติแชทเป็นโหมดส่วนตัว
  - `/reflect` = เก็บบทเรียนจาก 1 session มาปรับปรุง **skill**
  - `/correct` = จับความผิดพลาดที่เกิด ≥ 2 ครั้งมาปิดตายที่ **ตัว repo** (สถาปัตยกรรม > type/lint > test > doc)
  - `Eval playbook` = ทดสอบ skill ที่แก้แบบปิดตา (blind test) กันอาการ overfit
- **ข้อควรระวัง:** ห้ามแก้ skill ปนเข้าไปใน PR งานฟีเจอร์ — แยก PR ต่างหากเสมอ
