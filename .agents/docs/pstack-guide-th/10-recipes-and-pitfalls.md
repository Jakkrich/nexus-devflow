# บทที่ 10: สูตรคำสั่งและกับดักที่ควรเลี่ยง

รวม Prompt ที่น่าก๊อปไปใช้ พร้อมกับดักที่ทุกคนมักเผลอพลาดกันคนละครั้ง แค่สลับชื่อ path กับเงื่อนไขจบงานของคุณเข้าไปแทน สูตรเหล่านี้จงใจเขียนแบบไม่เป็นทางการ เพราะนั่นคือวิธีที่พิมพ์ใช้งานจริง และ skill ต่างๆ อ่านเจตนาได้สบายมาก

![She tastes a finished dish while robots cook from a recipe box, with pinned cards reading /how, /tdd, and /loop above the counter.](../images/recipes.jpg)

## ทำความเข้าใจระบบย่อยที่ไม่คุ้นเคย

```text
use /how first to understand how this initialization works. then use /why to figure out why it broke recently.
```

กลไกการทำงานมาก่อน ประวัติศาสตร์ตามมาทีหลัง รายงานของแต่ละ skill จะบอกแหล่งที่มาที่มันค้นหา คุณจึงรู้ว่าคำตอบอิงจากหลักฐานไหน

## ให้ทวนปัญหาที่สับสนก่อนแตะโค้ด

```text
/poteto-mode read this thread. restate the underlying issue in your own words, in plain english. don't change any code yet.
```

ความเข้าใจผิดจะโผล่ตั้งแต่ตอนทวนความ ตรงจุดที่แก้ได้ด้วยข้อความเดียว เก็บทฤษฎีของคุณไว้กับตัวก่อนจนกว่า agent จะสรุปมุมมองของมันเองจบ ถ้าแค่อยากให้ทวนความอย่างเดียวโดยไม่เปิด playbook ใช้ `/in-your-own-words`

## ขัดเกลา Prompt ก่อนกดส่ง

```text
/sharpen write the onboarding doc for the new billing service.
```

agent จะชี้สิ่งที่ผู้เชี่ยวชาญจะทำเพิ่มในส่วนที่คุณไม่ได้ขอ วัตถุดิบเริ่มต้น วิธีและเครื่องมือ รวมถึงหลักฐานภายนอกที่จะพิสูจน์ว่าผลถูกต้อง แล้วส่ง prompt ฉบับปรับปรุงกลับมาให้คุณอ่านก่อน โดยยังไม่ลงมือทำจริง เมื่ออ่านแล้วถูกใจค่อยส่งออกไปใช้งาน

## ทำ Prototype ก่อนตัดสินใจเลือก

```text
/poteto-mode prototype a few options for the settings layout. put them behind a switcher and send me screenshots of each.
```

เลือกจากของที่รันได้จริง ไม่ใช่จากคำบรรยาย โดย agent จะตอบคำถามเรื่อง layout และ timing ที่ค้างคาไปให้ในตัว

## แปลง Design ที่นิ่งแล้วให้เป็นแผน

```text
/poteto-mode turn this design into a plan. small verifiable PRs, each with its own proof.
```

สั่งขั้นตอนนี้เฉพาะหลังจาก design ลงตัวแล้วเท่านั้น สิ่งที่ได้คือไฟล์แผนซึ่งระบุ playbook ที่จะใช้รันในแต่ละขั้น

## ขอความเห็นที่สองสำหรับงานออกแบบ

```text
ask /arena for a second opinion on this thread and our approach
```

ดีไซน์ปัจจุบันของคุณจะกลายเป็นหนึ่งในตัวเลือกที่เข้าประชัน แล้วรายงานสังเคราะห์จะบอกว่าคณะกรรมการเจอทางเลือกที่ดีกว่าหรือยืนยันว่าแนวทางเดิมดีอยู่แล้ว ต้นทุนแค่นี้ถือว่าถูกมากเมื่อเทียบกับดีไซน์ที่แก้ย้อนกลับแพง

## ตรวจงานหลายชิ้นที่อิสระต่อกันแบบขนาน

```text
/swarm check every package under packages/ against its check.sh. one worker per package. one report.
```

worker แต่ละตัวรับผิดชอบ 1 package ตัวหลักรอจนครบแล้วคืนรายงานเดียวที่สรุปสถานะ `PASS`, `ISSUES`, หรือ `BLOCKED` แทนที่จะโยน log ดิบจาก worker ทุกตัวมาให้คุณอ่าน

## รีวิว Branch แบบจับผิดอย่างจริงจัง

```text
/interrogate the whole branch, but skeptically. don't change anything yet. no nitpicks unless it's an actual bug or regression in behavior.
```

คำขยายความด้านหลังทำงานจริงจัง `"don't change anything yet"` ล็อกให้เป็นแบบ read-only และกฎห้ามจับผิดจุกจิกช่วยกรอง noise ออกไป เหลือเฉพาะจุดที่พิสูจน์แล้วว่าเป็นบั๊กหรือทำของเดิมพัง

## แก้บั๊กด้วยการเขียน Test ที่พังก่อน

```text
/poteto-mode repro the duplicate write first. if there's a cheap test path, /tdd it. then fix and rerun.
```

วลี `"if there's a cheap test path"` สำคัญมาก การฝืนเขียน test ผ่าน mock ที่เปราะบางพิสูจน์อะไรได้น้อยกว่าการรันคำสั่งจริง และ playbook ได้รับอนุญาตให้บอกตรงๆ ได้ว่าเคสไหนไม่ควรฝืน

## จำลองให้พังและแก้พร้อมหลักฐานยืนยัน

```text
/poteto-mode repro this with /verify-<app>. if it repros on main, fix it and show me a video as proof.
```

`"if it repros on main"` เปิดทางให้รันหยุดได้ทันทีถ้าบั๊กนั้นหายไปแล้วบน main และวิดีโอช่วยให้คุณตรวจการแก้ได้ตั้งแต่ยังไม่ทันอ่านโค้ด diff

## พิสูจน์คุณสมบัติที่ Test ทั่วไปเอื้อมไม่ถึง

```text
/create-formal-verification-skill the retry queue. a message must never be delivered twice.
```

คุณจะได้การตรวจคุณสมบัติข้อเดียวครบทุกเคสในขอบเขตที่กำหนด ได้ counterexample ในภาษาโค้ดของคุณหากโค้ดปัจจุบันทำพังอยู่ และได้ skill ประจำโปรเจกต์ที่คอยเตือน agent ตัวถัดไปเมื่อมาแก้โค้ดส่วนนี้

## ตรวจความจริงของตัวเลขก่อนนำไปโพสต์

```text
/benchmark-checklist vet this 40% speedup before it goes in the pr description
```

ผลลัพธ์จะบอกว่าเร็วขึ้น ช้าลง ไม่ต่างอย่างมีนัยยะ หรือสรุปไม่ได้ พร้อมจำนวนรอบที่รัน, range, และตัวจำกัดของตัวเลขนั้น

## หยุดการแก้ความผิดพลาดซ้ำซากด้วยมือ

```text
/correct agents keep adding new config flags without registering them in the schema
```

ทางแก้จะลงไปฝังใน repo ในรูปสถาปัตยกรรม, type, lint, หรือ test เพื่อไม่ให้ agent ตัวต่อไปพลาดเรื่องเดิมอีก

## ถามวิธีใช้โดยยังไม่เริ่มรันงาน

```text
/poteto-help how do i get poteto-mode to stay on every turn?
```

คุณจะได้คำตอบ พร้อม prompt ที่นำไปส่งต่อได้ และลิงก์ไปยังแหล่งอ้างอิง โดยไม่มีการรันงานจริงจนกว่าคุณจะส่ง prompt นั้น

## คุมรันให้อยู่ในร่องในรอยตอนคุณไม่อยู่

```text
im going to bed, keep going autonomously until every fixture passes. do not stop. keep a decision log i can audit in the morning.
```

รายละเอียดเต็มดูใน [บทที่ 7](./07-overnight.md) รูปแบบสั้นๆ ด้านบนใช้ได้ทันทีเมื่อในแชทมีรายละเอียดงานและเงื่อนไขจบงานอยู่แล้ว

## ดึงสติรันที่กำลังออกนอกลู่นอกทาง

คำสั่งดึงทิศทางใช้แค่บรรทัดเดียว:

```text
i said the goal is to repro. i did not ask for a fix yet.
```

```text
apply prove it works. show me the real output, not the build log.
```

```text
/unslop that, no emdashes
```

คุณแทบไม่ต้องการคำพูดเยอะ แค่ใช้ชื่อที่ถูกต้อง และ [บทที่ 8: 24 หลักการ](./08-principles.md) คือคลังคำศัพท์ชุดนั้น

## ขอคำตอบเป็นภาษาคนง่ายๆ

```text
/bro
```

พิมพ์แค่นี้จบ [`/bro`](../../../skills/bro/SKILL.md) จะสรุปข้อความล่าสุดใหม่เหมือนคนคุยกับคน ตัดศัพท์เทคนิคและสั้นลง ใช้เมื่อคำตอบทางเทคนิคดูครบถ้วนสมบูรณ์แต่คุณอ่านแล้วยังไม่เข้าใจว่ามันพูดอะไร

## ตามข่าวแชทที่ปล่อยรันทิ้งไว้

```text
/ketchup
```

[`/ketchup`](../../../skills/ketchup/SKILL.md) เล่าด้วยภาษาคนว่าเกิดอะไรขึ้นบ้างตั้งแต่ข้อความสุดท้ายของคุณ แล้วลิสต์เรื่องที่รอคุณตัดสินใจพร้อมตัวเลือกที่แนะนำ หลักฐาน และความเสี่ยง โดยไม่แก้ไขโค้ดใดๆ ระหว่างรายงาน

หากอยากดูแบบภาพเคลื่อนไหวแทน ให้รัน [`/ketchup-video`](../../../skills/ketchup-video/SKILL.md) มันจะสรุปเหตุการณ์เป็นวิดีโอสไลด์สั้นๆ พร้อมคำบรรยาย และลิสต์สิ่งที่รอคุณตัดสินใจไว้ใต้คลิป

## กับดักที่ควรเลี่ยง

- **ไล่รายชื่อ skill ใน prompt:** `"use /architect then /arena then /interrogate"` มักสลับลำดับขั้นตอนที่ playbook จัดเรียงไว้ดีอยู่แล้ว แค่บอกเป้าหมายและข้อจำกัดพอ เอ่ยชื่อ skill เฉพาะตอนอยาก override ค่าปกติ
- **เงื่อนไขจบงานที่คลุมเครือ:** `"make it better"` ไม่ได้ให้อะไร `/loop` เอาไว้เช็ก ต้องให้คำสั่งหรือ artifact ที่ตัดสินผ่าน/ตกได้
- **นำด้วยทฤษฎีที่ตัวเองเดา:** agent จะวิ่งไปหาเฉพาะตรงจุดที่คุณชี้ ให้มันทวนปัญหาในมุมของมันก่อน แล้วค่อยแชร์ข้อสันนิษฐานของคุณ
- **คว้าดีไซน์แรกทันที:** การคิดรอบเดียวมักล็อกโครงสร้างแรกที่โมเดลนึกออก ขอ prototype หรือ `/architect` แล้วเลือกจากหลักฐาน
- **ขัดเกลาแผนบนกระดาษลอยๆ:** การเอาฝ่ายจับผิดมาสับแผนที่ยังไม่มีโค้ดรองรับ มีแต่จะปั้นความเสี่ยงเทียมที่ไม่เกิดขึ้นจริง เคลียร์คำถามเปิดด้วย prototype ก่อน แล้วค่อยรีวิวของที่สร้างขึ้นจริง
- **ปล่อย agent ขนานกันใน worktree เดียว:** พวกมันจะเขียนทับไฟล์กันเองจนแยกไม่ออกว่าใครแก้อะไร ให้รันผ่าน cloud agent หรือสั่งแยก worktree ต่อหนึ่งงาน
- **เปิด loop ก่อนไว้ใจ loop:** ลูปที่ตรวจงานตัวเองไม่ได้มีแต่จะผลิตขยะให้เร็วขึ้น ทำ verification skill ให้ใช้งานได้ก่อน
- **เชื่อตัวเลขที่ยังไม่ผ่านการสอบสวน:** warm cache หรือโค้ดที่วิ่งข้ามเส้นทางจริงปั้นตัวเลข speedup ปลอมๆ ได้ง่าย รัน `/benchmark-checklist` ก่อนเอาตัวเลขไปใช้ทุกครั้ง
- **คอยแก้ความผิดพลาดเดิมด้วยมือ:** การแก้ในแชทช่วยได้แค่รอบเดียว `/correct` แก้ที่ตัว repo เพื่อปิดไม่ให้รอบถัดไปพลาดซ้ำ
- **ใช้ `/arena` เพื่อไล่ตรวจให้ครบ:** `/arena` ทำโจทย์ดีไซน์หรือโค้ดเดียวกันซ้ำแล้วเอามาหลอมรวม ส่วน `/swarm` แบ่งชิ้นงานหรือแข่งกันแล้วสรุปรวมเป็นรายงานเดียว
- **เชื่อคอมเมนต์รีวิวทุกข้อ:** ทั้งบอทและคนมักปนจุดพลาดจริงกับ noise เข้ามาด้วยกัน `/interrogate` เก็บเฉพาะจุดที่รันซ้ำแล้วพังจริง และแสดงรายการที่ปัดตกไว้ให้คุณตัดสินใจกลับคำได้เอง
- **นึกว่า `auto` เป็นชื่อโมเดล:** `auto` และ `inherit-parent` แปลว่า "ละฟิลด์ model ทิ้ง เพื่อให้ subagent ใช้โมเดลเดียวกับแชทหลัก" (ดูรายละเอียดใน [บทที่ 1](./01-setup.md))
- **รายงานว่าสำเร็จจากผล build สีเขียว:** build แค่พิสูจน์ว่าคอมไพล์ผ่าน จงขอผลรันคำสั่งจริง, flow จริง, ค่าที่บันทึกจริง, หรือ profile จริงมาแสดงในคำตอบเสมอ
- **เขียน `SKILL.md` ขึ้นมาดื้อๆ ด้วยมือเปล่า:** ส่งเข้า [Authoring or modifying a skill playbook](../../../skills/poteto-mode/playbooks/authoring-a-skill.md) เพื่อผ่านการตรวจสอบความถูกต้องและการรีวิว

นี่คือทั้งหมดของคู่มือ หากคุณอ่านข้ามมา แนะนำให้ย้อนกลับไปที่ [บทที่ 1](./01-setup.md) แล้วลองรันงานจริงสัก 1 ชิ้น นิสัยการใช้งานจะติดตัวจากการลงมือทำจริง ไม่ใช่จากการอ่านเพียงอย่างเดียว

## สรุปท้ายบท

- **แก่นของบทนี้:** ความสำเร็จของ pstack ไม่ได้อยู่ที่การเขียน prompt ยาวเหยียด แต่อยู่ที่การรู้ว่า **"จังหวะไหนควรถาม / จังหวะไหนควรลอง / จังหวะไหนควรจับผิด"**
- **สูตรจำสั้นที่สุดสำหรับใช้งานจริง:**
  - งงระบบ → `/how` แล้วตามด้วย `/why`
  - สับสน → `/in-your-own-words` หรือ `/sharpen` ก่อนส่ง
  - ลังเลเรื่องหน้าตา/แนวทาง → `prototype` แล้วเลือกจากภาพจริง
  - ไม่ไว้ใจโค้ด → `/interrogate` หรือ `/blast-radius`
  - พลาดซ้ำ → `/correct` | ขยะเยอะ → `/deslop` + `/no-comments` | อ่านไม่รู้เรื่อง → `/bro` | ปล่อยรันทิ้งไว้ → `/ketchup`
