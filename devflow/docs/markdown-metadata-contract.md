# Markdown Metadata Contract

This contract defines the default metadata and heading-tag standard for every Markdown file generated by Nexus-DevFlow agents, workflows, and templates.

The goal is to keep Markdown useful in three places simultaneously:
1. Human reading in GitHub, code editors, and PR reviews.
2. Obsidian vault navigation, graph search, and Dataview-style querying.
3. Agent and script indexing without forcing every report type into an unnatural shape.

---

## 1. Core Rule

Every generated `.md` file should use a hybrid metadata model:
1. A shared **YAML frontmatter core** at the top of the file.
2. Optional **type-specific frontmatter fields** based on `doc_type` and `category`.
3. **Obsidian-compatible heading tags** at the end of headings for section-level semantic meaning.

---

## 2. Required Frontmatter Core

```yaml
---
id: "md-YYYY-MM-DD-slug"
title: "Human-readable title"
doc_type: "report"
category: "general"
status: "draft"
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
owner: "agent-or-human"
source_workflow: null
related_task: null
related_files: []
tags:
  - nexus-devflow
aliases: []
summary: "One or two sentence summary."
metadata_version: 1
---
```

### Required Field Meanings:

| Field | Type | Meaning |
| :--- | :--- | :--- |
| `id` | string | Stable unique identifier for this document (e.g. `001-user-auth`, `DISC-20260825-001`, `ADR-001`). |
| `title` | string | Human-readable document title matching or mirroring H1. |
| `doc_type` | string | Broad document kind (`spec`, `plan`, `discovery`, `decision`, `report`, `guide`, `changelog`). |
| `category` | string | Workflow category (`planning`, `qa`, `security`, `release`, `architecture`). |
| `status` | string | Lifecycle state (`draft`, `in-progress`, `completed`, `accepted`, `archived`). |
| `created` | string | Creation date in `YYYY-MM-DD` format. |
| `updated` | string | Last update date in `YYYY-MM-DD` format. |
| `owner` | string | Responsible agent role or human developer. |
| `source_workflow` | string \| null | Command that produced the document (e.g. `/feature`, `/audit`, `/grill`). |
| `related_task` | string \| null | Task ID, issue ID, or PR ID. |
| `related_files` | string[] | Array of repository paths described or affected. |
| `tags` | string[] | Obsidian tags without `#`. |
| `aliases` | string[] | Alternative note aliases. |
| `summary` | string | Short summary for search and index tables. |
| `metadata_version`| number | Contract version (`1`). |

## 3. Optional Frontmatter By Document Type

### A. Living Spec (`current-feature.md`)
```yaml
doc_type: "spec"
category: "planning"
stage: "current-feature"
source_discovery: "DISC-20260825-001"
source_idea: "IDEA-001"
```

### B. Pre-Flight Discovery (`discovery.md`)
```yaml
doc_type: "discovery"
category: "architecture"
decision: "Proceed"
selected_route: "Direct"
related_ideas: ["IDEA-001"]
```

### C. Architecture Decision Record (`ADR-xxx.md`)
```yaml
doc_type: "decision"
category: "architecture"
status: "accepted"
deciders: ["Lead Architect", "Security Auditor"]
```

### D. QA Verification & Audit Report
```yaml
doc_type: "report"
category: "qa"
qa_result: "pass"
risk_level: "low"
finding_count: 0
```

## 4. Heading Tag Contract

Heading tags describe section semantics in Markdown body text (placed at the end of heading lines):

```markdown
# Living Spec: User Authentication #doc/spec

## 🎯 1. Define & Boundaries #section/scope

## 📐 2. Technical Spec & Contracts #section/contracts

## 📋 3. Execution Plan & TDD Checklist #section/tasks

## ⚡ 4. Implementation Log & Evidence #section/evidence

## 🧪 5. Multi-Lane Verification Matrix #section/verification

## 📦 6. Release Digest & Retrospective #section/summary
```

### Standard Section Tags:
- `#section/summary`, `#section/scope`, `#section/contracts`, `#section/tasks`
- `#section/evidence`, `#section/verification`, `#section/findings`
- `#finding/bug`, `#finding/security`, `#finding/performance`, `#finding/gap`
- `#priority/critical`, `#priority/high`, `#priority/medium`, `#priority/low`

---

## 5. Agent Authoring Checklist

Before creating or updating any generated Markdown file:
- [x] Include the required YAML frontmatter core at the top.
- [x] Use appropriate `doc_type` and `category`.
- [x] Ensure tags in frontmatter do not include `#`, while heading tags do include `#`.
- [x] Keep `updated` timestamp synchronized upon edits.
- [x] Use relative Markdown file links for cross-document navigation.
