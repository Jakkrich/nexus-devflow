01

What (คืออะไร & ทำอะไรได้บ้าง)

Ponytail คือ Skill & Mindset จำลองแนวคิดนักพัฒนาอาวุโส (Senior Developer) ที่ยึดคติ "The best code is the code you never wrote" เพื่อป้องกันไม่ให้ AI Agent สร้าง Abstraction ซ้ำซ้อน หรือติดตั้ง dependencies ภายนอกพร่ำเพรื่อ

  • Decision Ladder — บันไดการตัดสินใจ 7 ขั้น ค้นหาทางออกที่กระชับที่สุดก่อนเขียนโค้ด
  • Root-Cause Bug Fixing — ซ่อมบั๊กที่ shared caller กลางจุดเดียว ไม่แก้แบบแปะปลาสเตอร์ (Band-aid fixes)
  • Intensity Modes — เลือกระดับความลีนได้ตามงาน: lite, full (default), ultra, audit, debt
  • Dependency Hygiene — ใช้ฟังก์ชัน Built-in / Runtime stdlib ก่อนพิจารณาลง npm package ใหม่
02

Why (ทำไมต้องใช้ & ประโยชน์ที่ได้รับ)

โดยธรรมชาติ โมเดลภาษา (LLM) มักมีแนวโน้มที่จะ Over-Abstract สร้างไฟล์ย่อยๆ จำนวนมาก และสร้าง wrapper ครอบไปเรื่อยๆ ซึ่งส่งผลเสียในระยะยาว:

  • ลด Token Consumption — ประหยัดบริบทหน้าต่าง (Context Window) โดยเฉพาะในการรันลูปอัตโนมัติหลายฟีเจอร์ (/continuous)
  • ลดหนี้ทางเทคนิค (Technical Debt) — ยึดหลัก Boring over clever และ Deletion over addition
  • อ่านโค้ดง่ายขึ้น — โค้ดตรงไปตรงมา ดูแลรักษาง่าย ไม่ต้องไล่ตามคลาสเชื่อมต่อหลายชั้น
03

Who (เหมาะสำหรับใคร)

  • Backend & Logic Developers — ผู้พัฒนา REST API, Middleware, CLI, และ Data Pipeline
  • Bug Fixers & Maintainers — ผู้แก้บั๊กผ่านสเตจ /fix หรือ /debug
  • Solo Developers & Tech Leads — ที่ต้องการคุม Codebase ให้สะอาด เล็ก และอ่านเข้าใจง่าย
04

Where (ใช้กับส่วนไหน & ขอบเขตความปลอดภัย)

🛑
Aesthetic Protection Gate: Ponytail ถูก ห้ามทำงาน ในงาน Web Frontend, UI Components, Styling (.css, .tsx) และสเตจ /prototype โดยเด็ดขาด เพื่อรักษาความสวยงามระดับพรีเมียม
ขอบเขตงาน (Scope) สถานะ เหตุผลและแนวทาง
Backend / CLI / Core Logic ACTIVE ลดความซับซ้อน ป้องกันการเขียน Wrapper ซ้อนกัน
Bug Fixing (/fix, /debug) ACTIVE บังคับแก้ที่จุดศูนย์กลาง (Shared function) จุดเดียว
Code Audit (/audit) ACTIVE สแกนหา Single-implementation interfaces และ dead abstractions
Frontend / UI Mockup (/prototype) AUTO-BYPASS ต้องคง Micro-animations, Glassmorphism, และ Typography ระดับพรีเมียมไว้
05

When (ควรใช้ตอนไหน & ลำดับก่อน-หลัง)

  • ในสเตจ /implement — เมื่อเข้าสู่ TDD Green Phase เพื่อเขียนโค้ดที่สั้นและตรงไปตรงมาที่สุด
  • ในสเตจ /fix — เมื่อต้องการแก้บั๊กให้จบที่ต้นตอของฟังก์ชันส่วนกลาง
  • ในสเตจ /audit — ก่อนทำ Release เพื่อสแกนดูว่ามีไฟล์หรือ class ไหนที่เกินจำเป็น
  • ห้ามใช้ในสเตจ /discovery, /brainstorm — เพราะช่วงระดมไอเดียต้องการมุมมองที่กว้าง ไม่ควรถูกจำกัดด้วย YAGNI ตั้งแต่แรก
06

How (ใช้งานอย่างไร & บันได 7 ขั้น)

เมื่อทำงานในฝั่ง Backend หรือ Core Logic ให้หยุดที่ขั้นแรกที่แก้โจทย์ได้สำเร็จ:

1
Does this need to exist? (YAGNI) — ถ้าเป็นความต้องการล่วงหน้า ให้ข้ามเลย
2
Already in this codebase? — ตรวจสอบ helper, util ที่มีอยู่แล้ว นำมา reuse ห้ามเขียนใหม่
3
Standard library does it? — ใช้ Node.js / Runtime built-in ก่อนเขียนเองเสมอ
4
Native platform feature covers it? — ใช้ฟีเจอร์พื้นฐาน เช่น DB constraint แทน app logic
5
Already-installed dependency solves it? — ใช้ library ที่ลงไว้แล้ว ห้ามลง package ใหม่เพื่อโค้ดไม่กี่บรรทัด
6
Can this be one line? — รวบเป็นบรรทัดเดียวถ้าอ่านรู้เรื่องและปลอดภัย
7
Only then: minimum code that works — เขียนโค้ดให้น้อยที่สุดที่ทำงานได้ถูกต้อง
